PRESERVATION DECISION (2026-11-11)
---------------------------------
For this work, the executable behavior of the preserved LegacyCode branch is
the preservation baseline. Thesis descriptions that disagree with it remain
recorded as unresolved historical descriptions. This decision does not imply
that a discrepancy is approved for correction, nor that current behavior
automatically matches the legacy program for every input.

ARCHITECTURE AND ENCODING
-------------------------
The thesis (PDF pp. 14, 16–21) describes a Harvard load/store processor with
four stages IF, RS, EX, WB; sixteen 8-bit registers, including CN=R12, HA=R13,
PS=R14, PC=R15; and 14 instructions. R0 is fixed at zero, and ordinary
instruction writeback must not overwrite R15. Instruction words are 16 bits:
bits 15–12 are opcode, bits 11–8 normally select a destination, and the low
byte holds source selectors or immediate data. The source files agree on the
widths: InstMemory has 256 words; DataMemory has 256 bytes; RegFileMemory has
sixteen bytes. See memory/*Memory.java and Simul/Simulator.java.

Opcode  Mnemonic  Thesis form or meaning       Legacy/current implementation
0       ADD       Rd,Rs1,Rs2; signed addition  Same fields; ALLU.exMux case 0
1       SUB       Rd,Rs1,Rs2; signed subtract  Same fields; case 1
2       AND       Rd,Rs1,Rs2                 Same fields; case 2
3       OR        Rd,Rs1,Rs2                 Same fields; case 3
4       NOT       Rd,Rs                     Same destination/source; case 4

The table is supported by PDF pp. 18–21, Assembler/Assembler.java
(resolveOperands and Opcodes), Simul/NMETransf.java, and Simul/ALLU.java
(exMux). The thesis table has apparent typography errors: it prints "HTL"
and "NST" once, although its opcode table and both source trees use HLT and
NTS. These isolated spellings should not be adopted as alternate mnemonics.

CONFIRMED AGREEMENTS
--------------------
* The opcode assignments and principal operand fields match across thesis,
  assembler, decoder, and both execution implementations.
* The PDF (p. 23) says EX and WB control queues have depths 2 and 3; both
  simulator branches allocate those depths in Simulator's constructor.
* The PDF (p. 24) describes two dependency distances; DependResolver has
  level-1 and level-2 forwarding state in both branches.
* The PDF (pp. 49, 57) explicitly says Reset preserves instruction and data
  memories. Simulator.reset() does so in both branches. This is an intended
  behavior, not a reset defect.
* The PDF (p. 19) says HLT sets HA to FF. Both branches encode HLT as CD00,
  direct the result to R13, and stop step() once HA reads 255.

DISCREPANCIES OR UNRESOLVED RULES
---------------------------------
1. NTS equality. PDF p. 19 prints CN <= (Rc1 <= Rc2), while Word.lt2Complement()
   and ALLU.exMux case 9 implement strictly less-than in both source trees.
   Equal operands distinguish the two interpretations. Do not change the
   comparison without deciding which reference governs.

2. SHT direction and count. PDF pp. 17–18 says the shift works in both
   directions, but gives no precise signed-count encoding or overflow rule.
   ALLU.exMux case 5 in LegacyCode and current source calculates a directional
   result and immediately overwrites it with rA << rB. The final behavior is
   a left shift by the unsigned value of Rs2. The initial calculation uses
   Rs1 as the count, which looks inconsistent with the table. Neither source
   tree resolves the intended directional encoding.

3. HLT destination field. PDF p. 20 draws HLT with R0 in nibble 2, whereas
   the PDF's HLT semantics require HA=FF and both assemblers encode CD00
   (nibble 2 = R13). The diagram appears inconsistent with the prose and
   working implementation; preserve CD00 pending an explicit decision.

4. Interrupt sources and nesting. PDF p. 25 describes automatic illegal
   instruction/register and arithmetic-overflow interrupts, recognized after
   WB, and says nested interrupts are disabled. Legacy/current source exposes
   Simulator.intrAck() for external requests, but reserved opcodes 6–7 merely
   produce zero; the arithmetic helper clears out-of-range results without
   raising an interrupt; intrAck() has no visible nesting guard. Thus the
   prose describes capabilities absent from the inspected implementation.
   It is unclear whether these were specifications or future intentions.

5. Signed arithmetic extremes. PDF p. 14 calls arithmetic 8-bit two's
   complement, but does not define overflow result/exception precisely.
   Word.setValue2Complement() in both branches clears a result whose absolute
   magnitude reaches 128, including -128. This should be characterized, not
   silently converted to conventional modulo-256 arithmetic.

6. Branch and interrupt timing. PDF pp. 21–26 describes IF/RS/EX/WB
   overlap, branch flushes, three-deep PCQ, and PCR selection by flags.
   Simulator.step(), DependResolver.resolve(), ALLU.incrPC(), and pcState[]
   implement corresponding mechanisms, but the PDF lacks enough boundary
   detail to prove every cycle outcome. Current code added validity tracking
   and bubbles; LegacyCode lacks them. This is an intentional implementation
   difference that needs cycle-by-cycle characterization, especially startup,
   taken branches, halt, and interrupts.

7. RTI binary form. PDF p. 20 depicts R15 in nibble 2 for RTI, whereas the
   assembler emits B000 for bare RTI in both branches. ALLU uses opcode and
   PCR, rather than that destination nibble, to redirect PC. The diagram and
   emitted word differ, though the runtime mechanism may still satisfy the
   prose. Preserve existing binary output until this is resolved.

TIMING BASELINE
---------------
PDF pp. 21–23: instruction i occupies IF, RS, EX, WB in four successive
cycles; by cycle 4, four instructions overlap in distinct stages. The
simulator uses one call to step() per clock cycle. Queue depth and the order
fetch -> push -> resolve -> execute -> writeback support that model, but
stage-validity changes on the current branch alter startup and flushed
cycles relative to LegacyCode. The existing LoopRegression covers one
repeated SUB dependency; it does not certify all four stages or interrupts.

EXECUTABLE COMPARISON (2026-11-11)
---------------------------------
The checked-in LegacyCode class files (Java class version 45.3) ran under
OpenJDK 21 from an isolated /tmp export. The current tree was compiled with
Make. One reflection-based probe loaded identical raw instruction words into
each simulator, stepped 12 cycles per scenario, and recorded PC, X, PCR,
registers R1..R15, CN, and data address 04. It did not alter either ISA or
simulation source. The cases were ADD, SUB, AND, OR, NOT, SHT, SHT with FF
count, reserved opcodes 6 and 7, ZTS, NTS equal, NTS less, JCN taken, JCN
not taken, RTI, HLT, LDI, LDR, STR, ADD overflow, ADD negative-128, and an
external interrupt at cycle 6: 22 scenarios, 264 sampled cycles.
The probe was temporary; the recorded observations and the expanded
Simul.PreservationChecks are the retained artifacts.

In the sampled states, all observed PC, PCR, register, condition, and M[04]
values matched. X differed in five scenarios:
* ZTS, NTS-equal, NTS-less, and STR: from cycle 6 onward, LegacyCode retains
  a nonzero X while the current simulator shows zero.
* Taken JCN: at cycle 7, LegacyCode shows X=0x55 while current shows X=0.

The differences follow the current branch's explicit validity/bubble handling
and the legacy path's continued execution of zero-filled instruction memory.
This is an inference from the code and traces, not proof that no other program
can expose a register or memory difference. X is used by forwarding logic,
so its mismatch remains a preservation risk. The expanded
Simul.PreservationChecks locks matching architectural observations for all
14 named opcodes, both reserved opcodes, control flow, selected boundaries,
and one interrupt sequence. It does not assert parity for the differing X
states or exhaustively cover all operands and timings.

Representative legacy observations from the probe:
* A program consisting of HLT reaches HA=FF and PC=03 after step 3, then
  stops advancing.
* Equal-operand NTS leaves CN=00; less-than NTS sets CN=FF.
* A taken JCN to 08 reaches PC=08 on step 6; the otherwise identical
  untaken case reaches PC=06.
* An external interrupt requested after step 5 reaches PS=08 and PCR=02
  on step 6 in the selected program.
* 7F + 01 and 80 + 00 both yield R3=00 under the legacy signed helper.

NEXT PRESERVATION CHECKS
------------------------
Extend the representative comparisons to operand boundaries, repeated data
dependencies, all 256 memory addresses, nested interrupt requests, binary
load/save, and long-running sample programs. Test whether the X differences
can affect later register or memory values. Record both encoded words and
per-cycle state. Treat mismatches as evidence for review, not permission to
change ISA behavior.
